# 管理台文档写入回执

管理台现在把文档导入、整文件排队和归档纳入既有的待确认请求机制。HTTP 成功或一个任意对象不代表这些操作已取得匹配的业务回执。异常响应仍保留原事件，禁止另起写入，用户明确重试时发送同一份冻结请求；不是后台自动重试。

## 核对内容

三个操作均核对来源、事件编号、文档 UUID、明确的 replay 标志和零模型调用标志，不接受 dry-run 回执。导入还按本次已发送的文件快照核对文件名、由扩展名派生的格式、字节数、SHA-256、BOM、Agent 标签、项目、active/revision1、stored、去重标志和创建时间。它不在响应到达时重新读取文件选择器，因此不会把用户随后选择的另一个文件当成已经上传。相同文件的新事件可返回 already_imported，不要求再建一份文档。

排队和归档在用户点击卡片时额外冻结三个仅用于本地核对的元数据：文档 ID、字节数、版本。它们存为 pending.receipt_context，不加入服务器请求，也不改变后端接口、事件哈希或数据库迁移。显式导出的待确认文件包含这些元数据，但不包含页面令牌或授权函数；它不是跨会话导入/自动恢复功能。

整文件排队核对 journaled、需要审核、1–16 条返回片段、片段内记忆 ID 与任务 ID 各自不重复、queued、合法 SHA-256 形状和 UTF-8 字节单位。范围必须从零连续覆盖所选原文件，无间隙、重叠、越界或空片段，每段不超过 32768 字节；非末段至少 32765 字节，与现有按 UTF-8 码点回退至多三个字节的整文件算法一致。本管理台没有“手工挑选部分片段”的入口；其他客户端的显式 fragments API 不在此校验器范围内。

归档核对所选文档 ID、所选版本加一、archived、归档时间、原文保留标志，以及合法的非负片段/任务/派生项计数。不强求这些计数等于旧列表上的数量，因为并发排队或任务处理可能改变它们。不会把归档解释为物理擦除。

## 不确定交付与历史回执

错误回执可能来自服务器已经完成操作之后的响应故障，因此“未确认”不表示“没有写入”。登记仍须先取得匹配回执；导入重试仍检查原文件选择、项目和明确同意。会话变化、授权撤回或选择变化不能让旧请求重新发送正文。此前已存在的未知交付状态不会被后一次准备失败清除。

同事件重放确认的是原操作，不承诺文档、片段或任务现在仍处于当时状态。例如导入之后，文档可能已被另一次明确操作归档；其原导入事件依旧返回当时的 active/revision1，而刷新列表显示现在的 archived。不会修改历史回执来假装它是最新状态。

审核和文档写入仍不清空无关的编辑草稿。本阶段不增加自动文件扫描、自动模型调用、浏览器持久化、自动采集或额外的原文下载。

## 证明边界

这是对已公开接口字段与本次请求的一致性校验，不是密码学认证。导入 SHA-256 与已发送指纹匹配，不等于独立的磁盘持久化证明。排队时浏览器没有片段原文的本地副本，只核对片段指纹形状及范围结构；不能据此证明其内容哈希正确或任意返回边界一定落在码点上。服务器仍负责原文字节及 UTF-8 验证；真实集成测试另行用合成原文字节逐片段核验。日期解析仅检查有效日期，不证明时间真实性。

本轮不扩展任务取消/模型整理的逐字段回执，也不宣称模型调用 exactly-once 或无重复费用。现有 document_read 路径不在本轮扩展范围内；现有按原文下载后的指纹核验保持不变。没有修改 Node CLI、MCP 工具目录、服务权限或上游版本锁。

## 验证入口

`node --test test/personal-document-receipts.test.mjs` 执行实际浏览器脚本与模拟 DOM/HTTP 响应，并用 canonical personal-document-core 的归一化和分片结果校对边界。它不等于真实浏览器或 PostgreSQL。

`test/personal-document-receipts-browser.py` 由 `test/personal-recall-browser-fixture.mjs` 在隔离数据库启动的真实控制台下运行。浏览器用例在服务器真实提交后才破坏回执，要求显式同事件重放；分别检查去重、授权撤回、整文件分片、归档、原文下载和历史回执。数据库独立断言 6 事件、2 文档、2 片段和 2 个未运行且失效的任务，重试不得重复创建记录。它在已有预览/纠错/记忆回执阶段之后运行，有明确合成写入，不是全程只读或真实模型质量测试。
