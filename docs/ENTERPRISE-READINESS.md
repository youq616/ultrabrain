# 大型公司记忆库中枢：完成定义与生产准入

**当前状态：alpha，企业化基础开发中，不是生产验收完成。**代码和功能测试通过、原始两个项目功能等价、用户服务器部署，以及大型公司的生产适用性是四个不同结论。不能用版本号或少量功能测试替代后面三项。

## 已有基础与本轮进展

保留 Linux 服务与项目托管 PostgreSQL/pgvector，不要求外部数据库服务；一套原生页面、事实与向量数据。已有 MCP、来源/版本治理、项目续接、原始会话交付、受控事实召回、摘要引用、旧应用升级演练和自托管 n8n 节点。

0.9 新增：阻断 ultra 响应上的原生 hot-facts 侧通道；可选服务端 governed 工具白名单；显式源登记和读写/停用开关；共享数据库的每源/主体分钟额度；单进程并发上限；追加型准入/result 审计；可复现小型读负载脚本。实际结果只看具体候选 commit 的测试记录。

## 生产必须通过的门槛

|---|---|---|
| 身份与组织权限 | 企业身份提供商接入；用户/Agent/部门/项目角色；权限撤销、跨源泄漏和委托调用专项测试；所有公开入口受同一边界管理。 | 完整单源授权不是完整组织 RBAC/ABAC；目录/委托/联合授权的 governed 产品化尚未完成；native 管理面需独立安全审查。 |

| 性能与资源公平 | 代表实际数据规模、读写比例、向量维度、并发和模型配置的可重现基准；冷/热缓存、长时间运行、突发和过载测试；区分业务拒绝与服务失败。 | 只有功能并发和小型热页读负载；没有大型语料的容量结论或分布式并发控制。 |

## 推荐的验收方式

先收敛一个可量化的 V1 试点，而非承诺“解决所有 Agent 记忆问题”。建议按**相互隔离的部门数据源 → 项目与 Agent 调用 → 治理召回 → 审计与恢复**逐层验收。测试数据不得包含未经同意的企业秘密。

容量报告必须固定：代码 commit、上游 pins、操作系统/CPU/RAM/磁盘、数据库设置、页面/事实/附件数量、数据分布、向量模型及维度、并发数、每类操作比例、持续时间、错误预算及测试集版本。不采用只重复读一个空页面得出的“可支持万人”数字。

建议先建立 10 万页面、100 万事实、20 个数据源的**候选测试档位**，在明确读写比例下测量，而不是将这些数字作为已支持容量。负载目标、SLO 和 RPO/RTO 在具备测试结果前均不得填“通过”。真实业务分布与模型配置可能让更小数据量也成为瓶颈。

高可用后续仍可采用由项目自行管理的 PostgreSQL 主备节点，不需要改为第三方外部数据库服务；这只是保留原需求的设计方向，当前未实现/部署。

## 开发顺序

P0：治理入口完整性与数据隔离；随后完善审计生命周期、容量和备份/故障恢复。P1：组织权限、全部事实消费入口和历史迁移，以及真实语义质量。P2：多模态解析、附件与跨文档摘要树等功能等价收尾。不同阶段可有重叠，但没有完成全部生产门槛前保持 alpha，不以频繁发版代替验收。

只有每个生产门槛有证据、应用部署通过验收、未解决问题有明确风险处置后，才能宣布“企业 V1 验收完成”。持续吸收上游功能属于后续维护，不应把“未来永远不再更新”作为项目完成条件。
