# 管理台写入回执与草稿保护

HTTP 成功不是写入确认。管理台现在对结构化记忆提交、原文入队、记忆更新和审核，按既有服务端合同核对回执；前置 Agent 登记也必须得到匹配的来源、标签、主体键格式、版本与 replay 标志。回执不符、空结果或含糊/矛盾的 JSON 成功与错误封套不会清除待确认请求或假报成功。

## 校验范围

commit 核对 source_id/event_id、完整条目数量、每条唯一 UUID/revision1/candidate，以及 stored、零模型调用和需要审核；capture 核对 source/event、原文和任务 UUID、原文版本1、queued/journaled、零模型调用和需要审核。update/review 核对所选记忆 ID、expected_revision+1、预期状态、replayed；更新还要求 review_required。更新和审核的既有回执不返回来源或事件编号，本阶段没有新增后端字段或修改历史事件。若以后返回这些可选字段，则不能与原请求矛盾。

这些校验仅确认回执与原请求的已公开合同一致，不是密码学认证、正文逐字存储证明或防恶意同账号代码的隔离机制。更新/审核不宣称得到不存在的 event_id 回显；真实服务端仍负责认证、版本冲突与原事件幂等。来源和页面会话在每次前置操作、发送和确认边界复核。

文档导入/排队/归档、任务取消与模型整理本轮只沿用原有业务回执处理，受通用 JSON 封套及会话检查保护；没有宣称它们已经新增完整的逐字段回执校验。尤其模型整理不是 exactly-once，不因本阶段而获得无重复费用保证。

## 不确定交付与显式重试

前置登记未确认时，不发送目标正文。若目标写入可能已发送而回执无效，保留原请求、原事件编号和不确定交付状态，禁止开启另一写入；显式重试仍发送同一份递归冻结的 JSON 请求，不生成新事件。已知的旧写入不确定状态不会被后来一次登记失败或拒绝抹掉。错误信息区分“本次目标写入未发送”和“此前/本次写入未确认”；不确定并不表示服务器一定收到请求。

取得有效重放回执只确认原事件，不能据此推断记录现在仍处于原版本或状态。确认之后的页面刷新错误不重新创建待重放写入。待确认请求可继续明确导出；页面会话令牌和授权函数不作为数据导出，本阶段不增加文件导入或跨会话自动恢复功能。关闭页面仍可能失去内存里的待处理状态，应保护显式下载的含正文文件。

## 已保存请求与新草稿分开

开始提交时记录编辑表单的选择。有效回执到达后，只有属于这次编辑的 commit/capture/update 且表单仍与最初选择一致，才重置编辑器。用户在等待期间改动正文、元数据或撤回保存同意时，原请求可得到确认，但新草稿保留、保存同意清除；不会假称服务器未保存，也不自动把新草稿切换到新的版本基准。需再次保存时仍核对版本，必要时使用已有人工对照。

审核、文档操作和任务操作不清空与它们无关的编辑草稿。表单比较是请求边界的选择快照，不是逐键历史记录；不承诺检测两次检查之间发生又恢复的瞬时变化。管理台仍不自动持久化草稿、不自动调用模型。

## 验证

Node 用实际浏览器 JS 和明确模拟 HTTP 覆盖错误回执、登记拦截、重复条目、不可变重放及草稿变化。新增 Chromium 阶段在真实控制台/数据库完成操作后，仅篡改送回浏览器的回执，验证拒绝、显式重放及真实表数据增量。它有明确合成写入，不是只读测试，不使用用户内容或真实模型。最终 SHA、CI 与独立复审结果记录于 PR #20。
