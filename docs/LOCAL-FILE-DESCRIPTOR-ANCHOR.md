# 本地文件身份：双只读句柄核验

本模块基于 PR46 的精确提交 `b81dd4c334fd4d0b77682eb374703d74a987fa53`，继续修正客户端 profile 与采集队列的底层叶文件读取，不重复增加暂停、恢复、健康检查或网络操作。

## 为什么需要另一种核验

上轮真实 Windows 22.16 工件 `11041588026` 的原生探针返回：路径与句柄设备号都在 unsigned32 范围，数值关系未识别，但 inode 与其他比较字段相同；探针在 identity 阶段失败。这个观察说明“路径宽64位对应句柄低32位”不是所有环境都满足的充分适配规则。工件没有输出真实设备值，本轮测试中的701/909或101/303均为明确合成值，不是从原机器采集的标识。

仅把两种设备号忽略掉会削弱检查。本模块为不能直接比较的 Win32 样本增加第二个独立、只读、同时持有的句柄：通过所选路径再次打开，并将它与第一个句柄在同一个统计域中做完整比对。不会尝试猜测新的掩码或根据操作系统版本放行任意数值。

## 核验顺序

原有精确及已知方向性比较仍使用原快速路径。只有 Win32、两边均为有效且非零的 native64 表示、且其他文件字段完全匹配时，才允许进入第二句柄路径。其他平台设备号不一致继续拒绝；零值或超范围值不能触发此适配。

读取前，第一句柄和第二句柄的 dev、inode、mode、nlink、UID/GID、size、mtimeNs、ctimeNs、birthtimeNs 必须逐项全宽相等。再次读取路径元数据，要求其与最初路径样本全宽相等，并与句柄的其他字段一致。两个句柄都保持打开，之后才读取第一个句柄的字节。

读取后再次核对两个句柄及最终路径。路径域内的设备号不能变化，句柄域内的设备号也不能变化；第二句柄指向不同文件、正文长短变化、时间戳变化或最后路径被替换，都会拒绝整次结果。只在所有检查和两个关闭操作均成功后交付字节。每个已打开的句柄只尝试关闭一次，首个失败不被后续关闭失败覆盖。

这是可信本地目录内的有限采样竞态检测，不是恶意同用户进程沙箱、Windows ACL/卷序号认证或事务快照。不能排除检查之间替换后恢复、文件系统伪造或复用全部身份元数据、底层文件标识碰撞。新增第二次打开的费用只发生在不能直接比较的 Win32 分支；它不增加任何写权限。

## 原有边界不变

profile 大小上限仍为16KiB；队列叶文件上限220000字节，可由调用方进一步缩小。验证精确大小后只分配大小加一的缓冲，使用显式偏移读取并拒绝增长/截断。队列单硬链接、profile原有硬链接政策、父目录/工作区/授权检查以及平台原有权限规则不变。没有chmod、删除、锁抢占、原生IO重试、网络重试或文件格式迁移。

诊断增加 anchor-open、anchor-before、path-anchor、anchor-after、anchor-close 等固定阶段，不输出路径、设备号、inode或正文。真实本地诊断仍由WeakMap标记；子进程序列化报告只按固定字段/枚举投影，不能变成认证过的本地错误或服务器回执。线程/进程压力报告现在保留有界的嵌套 file_read 诊断，未知字段和原因不会透传。

## 可执行验证

`node --test test/local-file-read*.test.mjs test/local-file-anchor*.test.mjs`运行旧检查和新增的独立句柄、真实路径替换、截断、权限、别名及失败顺序检查。本地Win32统计替身明确不等于原生Windows。

`node scripts/check-local-file-read.mjs`只操作临时合成文件，保留200次基础读取、一次profile别名读取与队列别名拒绝。若原始设备关系无法直接比较，输出仍为 `device_relation:unrecognized`，并标记 `confirmation:dual-descriptor-required`；必须经过真实读取器成功后才输出passed，不把关系改写成相等。无用户路径、原始标识或模型调用。

`node test/local-file-read-package.mjs /absolute/unpacked/ultrabrain-client`执行最终打包CLI、真实文件IO及官方SDK导入；保留原生、无符号和有符号场景，再增加独立32位设备域的完整队列操作，以及故意让第二句柄身份不一致的拒绝检查。后两类属于明确注入统计，不是Windows证据；所有场景均不启动服务器。

既有Ubuntu/Windows × Node22.16.0/22矩阵、25轮八进程竞争测试和实际安装包任务保留，并追加新测试。仍须读取新完整SHA的原生Windows与独立审核结果；原来锁创建EPERM、其他全量失败不因本模块的Linux通过而被宣布解决。先前的独立本地ceb11205版本没有混入此分支。

依据与证据：Node v22.16.0 的 `deps/uv/src/win/fs.c` 与 `src/node_file-inl.h` 解释不同统计调用及原生BigInt表示；额外的两句柄确认是本项目实现的保守策略，并非声称Node提供了原子路径认证。原生失败工件及执行日志见 `docs/reviews/local-file-anchor/` 与本轮交付报告。
