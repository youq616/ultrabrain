**Finding: EACCES alone does not identify which ptrace permission check failed. Matching user IDs does not establish access. A filesystem-group mismatch, nondumpable target, capability/user-namespace mismatch, or applicable LSM denial can independently explain it. Yama ptrace_scope is not a direct explanation for this READ check in the inspected kernel.**

The exact kernel path and conditions are:

1. `/proc/<pid>/exe` readlink uses `proc_pid_readlink`; it defaults to EACCES when `proc_fd_access_allowed` fails. That function calls `ptrace_may_access` with `PTRACE_MODE_READ_FSCREDS`. The boolean result discards the underlying denial code, so errno 13 cannot distinguish its stages. Ordinary path/procfs access constraints can also act before this point. Sources: [fs/proc/base.c, lines 674–687 and 1785–1802](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/fs/proc/base.c#L674), [proc_pid_exe(5)](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html).

2. Within `__ptrace_may_access`, same-thread-group introspection passes immediately. Otherwise this mode selects the caller's **filesystem UID and filesystem GID**, not merely its real/effective IDs. Both must match **all three target real, effective and saved-set IDs** in their respective classes; alternatively, namespace-aware CAP_SYS_PTRACE can satisfy this credential gate. Supplementary group membership does not substitute for the filesystem-GID comparison. A subsequent independent gate requires target `mm` dumpable to equal `SUID_DUMP_USER` (1), unless the caller is capable in `mm->user_ns`. The credential capability check uses `tcred->user_ns`, while the dumpability check explicitly uses `mm->user_ns`. These distinctions matter when namespaces differ. Only then does the LSM hook run. Source: [kernel/ptrace.c, lines 268–355](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/kernel/ptrace.c#L268).

3. The commoncap hook uses the caller's **effective capabilities** for FSCREDS. It allows this stage if caller and target share a user namespace and the target's **permitted** capabilities are a subset of the caller's effective set, or if the caller has CAP_SYS_PTRACE in the target credential user namespace. Neither identical UIDs nor an unrelated capability in a different namespace is enough. Commoncap applies this rule to both READ and ATTACH modes. Source: [security/commoncap.c, lines 135–156](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/security/commoncap.c#L135).

4. Yama's `ptrace_scope` switch is inside an ATTACH-mode condition. READ_FSCREDS contains READ and FSCREDS, without ATTACH; consequently this Yama access hook returns success for this operation, including when ptrace_scope is restrictive. This does not waive commoncap or other LSM checks. Changing ptrace_scope, the ancestry relationship, or PR_SET_PTRACER is therefore not supported by these sources as a remedy for this particular readlink failure. Sources: [security/yama/yama_lsm.c, lines 355–392](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/security/yama/yama_lsm.c#L355), [include/linux/ptrace.h, lines 62–72](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/include/linux/ptrace.h#L62), [ptrace(2), Yama discussion](https://man7.org/linux/man-pages/man2/ptrace.2.html).

5. Other LSMs can deny READ. The generic hook dispatches `ptrace_access_check`; AppArmor maps READ to its own ptrace-read permission, and SELinux checks FILE READ permission for this mode. Merely observing an LSM enabled does not establish that it denied this particular operation. Sources: [security/security.c, lines 948–950](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/security/security.c#L948), [security/apparmor/lsm.c, lines 123–139](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/security/apparmor/lsm.c#L123), [security/selinux/hooks.c, lines 2090–2101](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/security/selinux/hooks.c#L2090).

Important dumpability limits:

- Modern `CoreDumping` indicates a core dump currently in progress; it is **not** the dumpable permission attribute. The inspected status implementation provides that progress field and does not provide an authoritative target Dumpable value. Sources: [fs/proc/array.c, lines 414–464](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/fs/proc/array.c#L414), [proc_pid_status(5)](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html).
- PR_GET_DUMPABLE reads only the **calling** process. Calling it in a helper does not measure the manager. Source: [PR_GET_DUMPABLE(2const)](https://man7.org/linux/man-pages/man2/PR_GET_DUMPABLE.2const.html).
- Non-directory proc inode ownership can reflect a nondumpable target by switching to namespace root. However world-readable/executable directories such as `/proc/<pid>` intentionally retain effective process ownership, so that directory's ordinary-user ownership does not prove dumpable==1. Namespace mapping, a missing mm and concurrent state changes also limit the inference. Source: [fs/proc/base.c, lines 1814–1869](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/fs/proc/base.c#L1814).
- The namespace-read limitation is explicit in [fs/proc/namespaces.c, lines 42–89](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/fs/proc/namespaces.c#L42). ID ordering and user-namespace rendering are explicit in [fs/proc/array.c, lines 189–196](https://github.com/torvalds/linux/blob/e8f897f4afef0031fe618a8e94127a0934896aba/fs/proc/array.c#L189).
