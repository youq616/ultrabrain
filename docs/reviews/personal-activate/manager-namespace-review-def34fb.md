# Independent manager namespace diagnostic note

Reviewer: `/root/activate_recovery_review`. Application reviewed: `def34fb9577167bebc6f7d41d0c6bb8138220087`. This note supplements the BLOCK verdict in `recovery-review-def34fb.md`; it neither changes that verdict nor establishes the actual CI failure cause. No application or fixture code was changed.

The real first-plan failure is only `manager_process_unverified`. The wrapper in `scripts/personal_activate_manager.py:151–165` can produce that code while importing the shared verifier, reading the manager executable, or running `_process_snapshot`. Namespace equality is only one later condition inside `_process_snapshot`; a prior failure would never reach it.

I independently fetched [systemd's fixed v255 user manager unit](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/units/user@.service.in). It specifies `User=%i` and the `systemd-user` PAM stack, with no private network or PID namespace setting in that template. This does not prove what distribution drop-ins or the hosted runner apply. It does mean the template alone provides no evidence that an ordinary user manager must live in a different PID or network namespace from the CI caller.

The existing verifier compares the target process's PID and network namespaces with the caller, repeats those observations, and includes the namespace values in its process snapshot. The activation adapter records that snapshot in the graph contract and compares it during later observations; a newly observed namespace change therefore is not silently accepted. The same-manager recovery fence additionally requires the saved bus ID/unique owner and a departed sender, then validates identity again. It does not currently support an unproved cross-namespace PID translation.

For the fence itself, a pathname Unix D-Bus connection is different from the application's loopback HTTP/database relationship. This is an inference from the transport and process checks, not proof that the manager namespace check can safely be removed. The [D-Bus specification](https://dbus.freedesktop.org/doc/dbus-specification.html#bus-messages-get-connection-unix-process-id) defines the server-connected process ID, and [its Unix transport section](https://dbus.freedesktop.org/doc/dbus-specification.html#transports-unix-domain-sockets) distinguishes pathname sockets from Linux abstract sockets, which are network-namespaced. Supporting a manager in another PID namespace would require an explicit proof that the returned PID selects the intended local proc entry. A manager network-namespace difference would need a separately defined contract because console and PostgreSQL readiness still bind local processes and networking. Neither relaxation is justified by the current fixed error code.

A second independently verified hypothesis is proc readability rather than namespace inequality. The [Linux proc executable manual](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html) says executable-link access uses a `PTRACE_MODE_READ_FSCREDS` check. The [proc PID manual](https://man7.org/linux/man-pages/man5/proc_pid.5.html) describes how nondumpable tasks can expose proc entries as root-owned. The [dumpable attribute manual](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html) describes credential changes that reset the attribute. Thus an equal D-Bus UID does not itself establish that ordinary-user proc inspection succeeds. These current manual pages identify themselves as man-pages 6.19; no claim is made that the actual CI manager is nondumpable or has changed credentials.

Minimal distinguishing evidence from the disposable ordinary-user CI would be: whether initial executable readlink succeeds; the underlying exception class or allowlisted verifier code; whether executable file/parent ownership, mode and link-count conditions passed; whether the observed proc-directory UID matches; and booleans for PID/network namespace equality. Values should come from the same resolved manager PID while its owner is rechecked, with bounded reads and fixed filenames. No environment, memory, command-line secrets, user transcripts or service journals are needed. If initial readlink fails, namespace comparison has not yet been reached; if the fixed underlying result is `process_namespace_mismatch`, record the two equality booleans before proposing an exception. The actual failure remains unclassified until that evidence arrives.

No additional tests were executed for these hypotheses. The 259 Python/14 CLI final executions and carried-forward 51 capture/7 helper executions are documented separately with their exact SHA and fixture scope. Root and the other independent reviewer were informed of these distinctions.
