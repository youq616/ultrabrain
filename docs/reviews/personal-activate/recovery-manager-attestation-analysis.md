# Independent analysis of the manager executable-read refusal

Actual reviewer: `/root/activate_recovery_review`. This is a source and proof review following diagnostic candidate `70cd4cc3880c13c8d53d32627e5c771174a7d3c5`. It does not approve an implementation or change the whole-phase BLOCK recorded for `def34fb9577167bebc6f7d41d0c6bb8138220087`. No repository code or tests were modified.

## Current conclusion

Do not replace the manager executable/process verifier with D-Bus owner credentials plus public proc start ticks. Those values can identify a connection and a continuing process, but do not retain the present loaded-executable-inode, namespace and version/source assumptions. A root-system-manager launch attestation is a stronger alternative to investigate, but the proposed properties are not an equivalent current-image attestation. Preserve the refusal until the bounded CI metadata distinguishes the actual cause; if a disposable fixture credential mismatch is responsible, that permits a smaller correction while retaining the production verifier.

CI4 independently preserved diagnostics identify `scripts/personal_activate_manager.py:159`, the first `os.readlink('/proc/PID/exe')`, raising `PermissionError` errno 13. None of the subsequent shared verifier's UID, executable ancestry or namespace checks had executed. This disqualifies a namespace-mismatch diagnosis based solely on that error. The report `CI-FOURTH-SERVICES-AUDIT.json` contains the sanitized traceback and exact location. No assertion is made here that the target was nondumpable, held extra capabilities, had a different GID, or was affected by an LSM.

## What owner credentials and start ticks do and do not prove

The saved boot ID, bus ID and unique owner prevent silently switching to a different bus connection, and the daemon's peer UID/PID credentials are stronger than a service's self-reported strings. A descriptor-bound proc directory plus stable PID/start ticks protects observations against process exit and ordinary PID reuse when the PID coordinate system is established. None of these values by itself identifies the currently loaded executable image. `Version` is a reply from that owner, so it does not close the missing provenance by itself.

I executed a real bounded local counterexample using only a child I created: it first ran Python, then called `execv('/usr/bin/sleep', ...)`. The PID and `/proc/PID/stat` start ticks stayed identical while the loaded executable inode changed. The child exited normally; no D-Bus or systemd operation was performed. Results are in `recovery-exec-incarnation-counterexample.json`. This matches the [Linux execve documentation](https://man7.org/linux/man-pages/man2/execve.2.html): exec replaces the image in the existing process, and file descriptors survive unless marked close-on-exec. The test is not evidence that systemd performed such an image change in CI, or that its current bus descriptor survives arbitrary exec by default.

The existing source-based recovery argument is specifically about a v255 manager's synchronous same-UID authorization and job insertion. Simply deleting executable or namespace observations while retaining the same claim would leave that premise less substantiated. This is distinct from defending against every malicious same-UID operator, which the documented cooperative maintenance window already excludes. A changed trust model still has to be explicit and tested.

## Root-system-manager attestation: useful evidence with limits

The proposed fixed system bus and root-owned `org.freedesktop.systemd1` owner can provide an authority independent of the user manager for a root-launched `user@UID.service`. Root-controlled socket ancestry and typed root-manager properties are useful anchors. They do not make every property a record of the original spawn.

In particular, `MainPID == ExecMainPID` is insufficient. At [service.c:4366–4387](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/service.c), accepted `MAINPID=` notification can change the main process. `service_set_main_pidref()` at lines 203–205 also resets `main_exec_status`, so both properties may change together. The original command's runtime record must also be considered. [execute.c:466](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/execute.c) writes `command->exec_status` after the actual spawn; the [D-Bus service vtable](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/dbus-service.c) exposes the main status and command-list records separately. A configured argv with zero, missing or unrelated runtime status is not a launch proof.

Even a correctly correlated original command record establishes a launch history and current process association, not the current executable inode after an exec in that process. The current proc verifier observes the latter directly. A root attestation design must either obtain equivalent authoritative current-image evidence or declare a different proof scope and justify why the v255 source assumption holds in that supported scope. The current ordinary-user D-Bus property proposal has not established the equivalent evidence.

If this separate mode is pursued, these are minimum review requirements, not a declaration that the remaining proof is complete:

1. Fixed system-bus address, trusted root-owned socket ancestry, bounded direct messages with auto-start and interactive authorization disabled, and validated sender/serial/signature. Establish and record system-bus identity, root owner/credentials and the PID coordinate relationship; a number from another namespace is not a verified local proc selector. A socket's kernel credentials, daemon-reported credentials and namespace visibility have distinct meanings and cannot be assumed interchangeable.
2. Exact `user@UID.service` identity and service type, matching account, nontransient stable root-managed unit, valid root-controlled execution path, typed exact `systemd --user` command, and relevant execution-context restrictions. The proof must account for overrides, reloads and notified PID changes instead of assuming that a root-owned file name alone certifies the running command.
3. Active/running state, no unit job/control PID, nonzero stable InvocationID and a unique live ExecStart/ExecStartEx runtime record. Its PID must agree with the authenticated user-bus peer PID, MainPID and ExecMainPID; starts must be valid and exits absent. [execute.c:1793–1800](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/execute.c) records a `dual_timestamp_now()` value, so it must not be compared for exact equality with `/proc` start ticks without proving clock domains and rounding. Missing/reset runtime evidence must reject.
4. Bound proc observations using held descriptors and repeated UID/PID/start checks. Interleave these with repeated root-unit and both-bus identity observations around the user-manager graph and dispatch/fence. Treat any changed owner, incarnation, unit invocation, command record or failed read as refusal. The cooperative maintenance assumption still applies; this is not atomic exclusion of external root or same-UID actions.
5. Persist the proof method and complete root/user bindings with the activation intent. Recovery must reestablish the same method and bindings before fencing or accepting a terminal/ready outcome. It must not silently change from direct executable proof to launch-attestation proof after a crash or accept an old receipt as new readiness. Preserve the existing no-redispatch rule and application/console/PostgreSQL proc/HTTP checks.

These requirements add a second bus and trust path and need real ordinary-user integration, restart/reload/owner-change tests, notified-PID negative tests, journal compatibility review and exact-SHA independent review. They are substantially larger than a verified fixture credential repair. No fallback was implemented or approved by this reviewer.

## Strict outcome pending the next diagnostic

The immediate supported behavior is to keep `manager_process_unverified` for a caller that cannot obtain the required identity evidence. If the next read-only CI result proves a fixture-only credential problem, repair the disposable setup and rerun the original strict path. If the supported ordinary-user platform legitimately denies all equivalent current-image/namespace evidence, retain the documented limitation until a separately reviewed proof contract or authoritative read-only attestation exists. Broadening the scope cannot be justified by the current need to make CI green.
