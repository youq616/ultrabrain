Reviewer: `/root/activate_boundary_review/dbus_abi_crosscheck`.

Verdict: **NO BLOCKER found in the proposed distinction between parsing a passive `.swap` reference and authorizing traversal of a swap unit.** This conclusion requires retaining the pre-LoadUnit rejection of every `.device` or `.swap` node reached in the start, stop or verify closure. It is not approval of an exact candidate or the full phase.

The source proof is:

1. A cached inverse or ordering name is not itself a request to add that unit to the transaction. `RequiredBy` maps to stop/restart propagation, start-failure propagation, stop-when-unneeded pinning and default-target-dependency behavior. It has none of the atoms used to pull a unit into the console START transaction. `Before` and `After` each map only to an ordering atom. See [unit-dependency-atom.c, lines 16–99](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/unit-dependency-atom.c#L16).

2. For START, the transaction follows pull-in start, ignored start, verify and conflict-stop atoms. It follows reverse stop/restart propagation only for STOP, RESTART, or START with an explicit restart-dependencies flag. The product's fixed `fail` job mode does not set that flag: manager_add_job sets it only for JOB_RESTART_DEPENDENCIES. Therefore `.swap` in an active `-.slice`'s RequiredBy is not reached by the ordinary console START traversal. See [transaction.c, lines 1030–1129](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/transaction.c#L1030), [manager.c, lines 2055–2075](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/manager.c#L2055).

3. Ordering verification looks for a job already in the transaction or already installed on the other unit. If neither exists, it continues without adding one. It does not call the dependency-adding routine merely because a swap appears in Before/After. Existing external jobs can constrain ordering; that is different from initiating a new swap or Worker job. See [transaction.c, lines 445–472](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/transaction.c#L445).

4. Following-set expansion operates on the **unit actually receiving a transaction job**, before ordinary dependency dispatch. `unit_following_set` delegates only to that unit type's vtable; the slice vtable has no such callback. It does not walk arbitrary reverse dependencies looking for other types' following sets. Consequently a job on `-.slice` does not expand the swap's sibling inventory through its RequiredBy or Before references. See [transaction.c, lines 1012–1028](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/transaction.c#L1012), [unit.c, lines 4211–4219](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/unit.c#L4211), [slice.c, lines 416–462](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/slice.c#L416).

5. The original hidden-followers blocker still applies if a device or swap is actually reached. Canonical sys-* device Following can be empty while device_following_set returns same-sysfs siblings. Similarly swap_following can return NULL for a fragment-defined or canonical devnode unit, while swap_following_set returns other units sharing the devnode. A START job on that swap could therefore expand a sibling's dependencies even when its displayed Following is empty. Neither active state nor empty Following proves an empty following set. This is why the shared guard must remain before LoadUnit for start, stop and verify modes, rather than permitting a reached swap as an apparently passive unit. See [device.c, lines 952–1006](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/device.c#L952), [swap.c, lines 1264–1325](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/swap.c#L1264).

6. An already active, job-free non-anchor slice has a redundant START job which transaction cleanup can drop. The source nevertheless expands dependencies before this cleanup, so redundancy is supporting evidence, not the primary argument for allowing passive names. RequiredBy's start-failure handling also operates on already existing dependent START/VERIFY jobs; it does not create new dependent jobs. See [transaction.c, lines 276–308 and 727–738](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/transaction.c#L276), [job.c, lines 420–430 and 967–981](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/job.c#L420). No general claim is made about arbitrary concurrent external changes or unrelated existing jobs.

The observed working-tree implementation matches this distinction: `UNIT_NAME` at line 66 accepts `.swap` as a value in the cached dependency arrays, while the common nested `read` at lines 433–448 rejects both `.device` and `.swap` before `_read`/LoadUnit. Every pending start/stop/verify entry passes that guard at line 456. Passive values remain in the observed parent's cache, which is re-read and compared later; merely parsing them does not add an observed unit. If a `.swap` moves to Requires/Wants/BindsTo/Upholds, Requisite, conflict-stop reachability, or a reached stop unit's reverse stop propagation, traversal must reject it. The final reviewer should verify these cases and the original canonical-device regression on the committed candidate.

Origin context: v255's swap enumeration opens `/proc/swaps` without a system-manager-only guard, while `swap_is_extrinsic` identifies user-manager swaps as extrinsic. General slice dependencies add After/Requires toward the configured or root slice; swap-specific system default dependencies have a separate system-manager guard. This explains how passive cached swap references can be encountered without asserting that arbitrary user-manager swap activation is supported. See [swap.c, lines 81–85, 231–251 and 1336–1377](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/swap.c#L1336), [unit.c, lines 1516–1535](https://github.com/systemd/systemd/blob/db11bab38ccf1ed257f310d29070843d4c58ea01/src/core/unit.c#L1516).
